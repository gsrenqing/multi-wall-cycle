## 四、需求④：修正「必应每日壁纸」链接指向（v2.2 的 BUG）

### 4.1 v2.2 的问题

「必应每日壁纸」是下划线文字，点开却跳到 `https://cn.bing.com/` 首页，而不是当日壁纸归档页。

### 4.2 v2.3 的做法

- 规则地址：`https://bing.wdbyte.com/day/{yyyyMM}/{dd}.html`（4 位年 + 2 位月 / 2 位日），按**点击当时的日期**即时生成。
- 落点选择：先探测**当日页**，不可用再探测**昨天页**，都不可用则退回站点首页 `https://bing.wdbyte.com/`（你已明确接受这个降级）。
- 探测方式：**HEAD 优先 + 4 秒超时**，HEAD 被拒再退回 GET，只认 HTTP 200。结果按天缓存，同一天多次点击不重复发请求；点击期间鼠标显示为等待光标，失败时弹提示框（双语）。
- 为什么改探测方式：实测该站返回整页正文常需 3 秒以上，v2.3 最初用 2.5 秒 GET 探测，会把"今天"误判为不可用、退到昨天页。改 HEAD 后实测当日页命中。

### 4.3 实测记录（2026-11-13）

| 项目 | 结果 |
| --- | --- |
| `https://bing.wdbyte.com/day/202611/13.html`（当日） | HTTP 200 |
| `https://bing.wdbyte.com/day/202611/12.html`（昨日） | HTTP 200 |
| `https://bing.wdbyte.com/`（首页） | HTTP 200 |
| 程序内解析结果 | `https://bing.wdbyte.com/day/202611/13.html`（当日，耗时约 3.0 s） |

## 六、开机自启值名的处理

- 新值名 `MultiWallCycle`，旧值名 `多屏幻灯壁纸`。
- **启用自启时**：写新值名（命令带 `-min`，开机后只留托盘），并顺手删掉旧值名，避免开机同时启动新旧两个程序。

## 十、已知边界与取舍

1. **界面切换是中英两套完整文案，不是逐字翻译**。英文以"看懂、不被截断"为准，个别措辞（如 Enable this screen / Caption…）偏短，避免英文撑破卡片。
2. **必应勾选框的无障碍名不理想**。它是不带文字的方框，UI Automation 会把相邻标签「适配方式：」当它的名字。只影响读屏/自动化工具，不影响鼠标使用；下一版可补 `AccessibleName`。
3. **语言只影响界面，不影响壁纸文字描述的内容**。描述文字来自必应接口（中文站返回中文标题），切英文界面不会把图片描述翻成英文。
4. **v2.2 的两处历史取舍继续保留**：双勾（本地文件夹 + 必应）时本地优先；顺序轮换进度按显示器 DevicePath 绑定。

### 11.1 ①「关于」弹窗按内容收缩，1080×1920 竖屏也能完整显示

**根因**：旧实现把窗体尺寸写死为 `700×440`。单语化只减了文字、没减窗口，所以在 DPI 虚拟化（本机 175%）下，700 逻辑宽被放大到接近 1080 物理宽，在竖屏上横占近满屏、上下留大片空白——这正是你截图看到的形态。

**改法**（`MainForm.cs::AboutDialog`）：

1. 窗体尺寸 = **正文实测折行结果** + 内边距 + 底部按钮条，不再有常量尺寸。文字少则窗更小，一行不多给。
2. `AutoScaleMode.None`。本程序按系统 DPI 虚拟化运行（清单刻意不声明 dpiAware，见 `app.manifest` 注释），再叠加一次 WinForms 的字体缩放就是"字与行高错位、切半行"的来源；改成单层坐标后，系统缩放到任何 DPI 都是整体等比放大，不会切字。
3. 尺寸再**钳制到当前屏幕工作区的 90%**；万一正文过高，正文区转为可滚动，底部按钮永远可见。

**实测**（`-aboutgeom` 钩子，本机 2560×1440@175% → 工作区 1463×791）：客户区 **429×274**（窗口 435×303），正文 Label 359×180 @ (35,18)，按钮 100×34 居中，无越界。折算到 1080×1920@175% 的竖屏（逻辑工作区约 617×1050），429 宽只占约 70%，高度 274 约占 26%，可完整显示。

### 11.2 ②「文字描述」看不到 + 设置窗显示不全

分两条根因，都已经实测确认：

**(1) 看不到：两个原因叠加**

- **设置窗的「确定」按钮落在窗口外**。旧代码用 `btnPanel.ClientSize.Width - 220` 在构造期算坐标，那时 Dock 面板宽度还是默认 200，算出来是 `-20`——「确定」有一半在左边界外，视觉上更像「取消」，点了等于放弃修改，开关始终是关的。
- **白字关阴影时，在亮背景上真的看不清**。用你的 `CapitolReefSnow_…1920x1080.jpg` 实测：白字+无阴影压在雪景/亮天空上对比度极低，肉眼等于"没有"。渲染链路本身是好的（同图开阴影时文字清晰可读，已逐张验证）。

**改法**：

- 设置窗底部按钮改用窗体真实客户区宽度定位（右对齐），不再依赖面板成型时机；
- 关阴影时自动加一道"按背景亮度取黑/白"的 1px 对比影（`Bing.cs::RenderCaption` + `IsBrightRegion`）：亮底自动黑边、暗底自动白边，观感仍是"无阴影"；
- `Rect` 无效导致 `screenW=0` 时回退 1920×1080 估算，避免字号按 1:1 画进 4K 图后小到看不见；
- **点「确定」立即重绘当前这张图**（`WallpaperEngine.RepaintCaption`，不换图、不推进轮换进度），效果当场可见；该图确实没有描述时弹出说明（"这张图没有可用的描述文字，只有必应每日壁纸才带描述"），不再静默无声；
- 运行时若开着文字描述却没有描述可用，`log.txt`（测试版）记一行，便于下次现场定位。

**(2) 显示不全/吃半行：DPI 缩放下的系统性做法**

旧窗 `ClientSize=(430,470)` + 一堆魔法 y（12/52/108/232/280/330…）+ `ComboBox Size=(w,24)`，内容实际到 y≈508，超出视口靠 `AutoScroll` 兜底，于是"文字被吃半行"。

新窗（`CaptionSettingsForm.cs` 整文件重写）确立三条规则，后续任何界面都应照此办理：

1. **行高由字体度量算出**（`TextRenderer.MeasureText` 取实际行高 → 组合框高 = 行高+8、按钮高 = 行高+12、段间距 16），不再出现 24/26 这类魔法数字；字号变大、DPI 变高，行高自己跟着长。
2. **窗体高度 = 内容实际底部 + 固定按钮条**，并钳制到工作区 85%；放不下就内容区滚动，按钮条永远在底部。
3. **`AutoScaleMode.None`**，坐标一律按 96 DPI 逻辑像素算，交给系统统一放大；同时右侧留 16px，防止滚动条压住控件。

**实测**（`-capgeom`）：窗体 **440×498**，内容区 440×443、内容底部 431（无需滚动），右侧最大 437 ≤ 440，按钮「确定」254,12 / 「取消」343,12，均在 440×55 内，**无一越界**。

## 十二、v2.3 第三批反馈：程序图标 / 不使用本地文件夹 / 取消两个勾选框（2026-11-13 晚）

### 12.1 ①资源管理器里"没有图标"——因为 exe 里本来就没有图标资源

**根因**：这跟"图标没做好"是两件事。旧工程编译时从未给 csc 传 `/win32icon`，所以 exe 的 Win32 图标资源（RT_GROUP_ICON / RT_ICON）是**空的**，资源管理器只能画一张"白纸"；而托盘和窗口标题栏的图标是 `IconFactory` 在运行时用 GDI 现画的 32×32，跟 exe 文件本身无关——于是出现"托盘正常、资源管理器没有"的分裂现象。**只重画运行时图标永远修不好这个**，必须把图标真正编译进 exe。

**做法**：

1. 新写图标生成器 `_test\tools\IconGen.cs`（编成 `IconGen.exe`，用法 `IconGen.exe <out.ico>`）。它按"双屏 + 时钟"母题在 16/24/32/48/64/128/256 七个尺寸上**按尺寸等比重绘**（不是把 256 拉伸下来，小尺寸才不会糊成一团）；小于 256 的用 32bpp DIB（40 字节 BITMAPINFOHEADER + 自下而上 BGRA + 全 0 AND 掩码），256 用 PNG 压缩帧，手写 ICONDIR / ICONDIRENTRY 落成 `源码\app.ico`（105,643 字节，7 帧）。
2. 配色改过一次：首版时钟沿用旧的"白描边 + 白指针"，在白底预览里整个人消失。改成**白表盘 + 深靛蓝（#1E293B）轮廓与指针**；两块屏幕外圈原先那圈白色描边同样在白底上不可见，直接去掉（纯色块在深浅底上都够清晰）。深浅底对照预览（256 与 48 各两处）已确认可读。
3. 编译参数加两条：`/win32icon:源码\app.ico`（资源管理器、任务栏、Alt+Tab 用的 Win32 资源）+ `/resource:源码\app.ico,app.ico`（运行期读取的托管资源，资源名就叫 `app.ico`）。
4. `IconFactory.cs` 整文件重写：优先 `Assembly.GetManifestResourceStream("app.ico")` → `new Icon(stream)`，窗口/托盘/任务栏/资源管理器共用同一份图形；取不到才回退到原来的运行时绘制（回退图也同步改成白盘深指针）。每次返回独立副本，Form 与 NotifyIcon 各自持有、互不干扰。
5. `build.bat` / `build-test.bat` 同步加上这两条参数——**否则下次用脚本编译会把图标弄丢**，这类"改了源码却漏在脚本里"的坑很难事后发现。

**实测**：

- `IconGen` 输出后逐帧核对：7 帧、16/24/32/48/64/128/256 齐全，第 7 帧为 PNG 压缩的 256×256。
- 编出的 exe 用 `ExtractAssociatedIcon` 取回 **56×56**（系统按当前 DPI 取合适帧，说明 Win32 资源确实存在）。
- 托管资源核对：`GetManifestResourceNames()` 返回 `app.ico`，字节数 105,643，`new Icon(stream)` 读回 32×32——说明 `/resource` 也进包了。
- 用 `build.bat` 重新编一遍验证脚本本身可用（不是只验证我手敲的那条命令）。

### 12.5 一个编译参数上的坑（给以后复用的人）

PowerShell 里 `csc /resource:源码\app.ico,app.ico` 会把逗号解析成 PowerShell 的数组运算符，`$src` 也跟着被当字面量传下去，报 `CS1566 读取资源文件失败`。正确写法是**先把整串拼进一个变量**再传：

```powershell
$resArg = "/resource:" + $src + "\app.ico,app.ico"
$icoArg = "/win32icon:" + $src + "\app.ico"
& $csc ... $icoArg $resArg ...
```

cmd 下（`build.bat`）没有这个问题，可以照写 `/resource:源码\app.ico,app.ico`。

## 十三、v2.4：本地图片标题、入库写 EXIF、审查报告处置（2026-11-13）

### 13.1 先把"为什么本地文件夹一勾，标题全没了"查清楚

这一条不是猜的，是拿你机器上的真实文件探出来的（探针 `%TEMP%\DumpExif.exe`，只读不写）。

**根因一：描述链路前面有一道"文件名白名单"的门。**

`WallpaperEngine.cs` 里换图（`SwitchOne`）与重绘文字（`RepaintCaption`）两处，判断条件都是：

```csharp
if (rt.ShowCaption && ... && BingWallpaper.IsBingFile(src))
```

`IsBingFile` 只认三种名字：`Bing_YYYY-MM-DD.jpg`、`*_UHD.jpg`、`*_1920x1080.jpg`。名字不符就**连 EXIF 都不读，直接跳过**。你的 `D:\Pictures\竖屏壁纸` 里 125 张全是小红书导出名（`_1_莫失_来自小红书网页版.jpg`、`《中国国家地理》2027日历…_来自小红书网页版.jpg`），一张都不在白名单里——所以那个屏的标题"全军覆没"跟 EXIF 有没有内容无关，是根本没走到读 EXIF 那一步。

**根因二：我们自己存进文件夹的图，压根没有 EXIF。**

对 `D:\Pictures\必应壁纸` 的 200 张实测：

| 来源 | 样本 | APP1 Exif | XMP | GDI+ PropertyItems |
| --- | --- | --- | --- | --- |
| 《动态壁纸》下载的老图 | `波尔图大教堂.葡萄牙_UHD.jpg` | 1 | 2 | 11 |
| 本程序 11-02 起存的 | `AbrahamCanada_…_UHD.jpg` | 0 | 0 | 3 |
| 同上 | `AlpineBraies_…_UHD.jpg` | 0 | 0 | 3 |
| 同上 | `Atlantica_…_UHD.jpg` | 0 | 0 | 3 |

也就是说：程序每天确实把必应原图存进了文件夹（`BingDailyCheck()` → `TryDownloadToday(folder, true, …)` 一直在跑，这个功能**没丢**），但只往 `bing_meta.json` 里记了一行字，**图片本体是"裸"的**。裸图能显示标题的唯一来源就是那份 meta，而 meta 有两个天生缺陷：

- `MetaKeepDays = 90`：超过 90 天的条目被裁掉；
- 它跟着数据目录走（`%LOCALAPPDATA%\MultiWallCycle\bing_meta.json`），换机器、换目录、重装一次就没了。

`AlpineBraies_…_UHD.jpg`（11-03）实测既无 EXIF 也无 meta 条目——这就是"只靠 meta"必然丢字的活证据。这也正好对上你说的"11 月 2 日至今的 7 张缺标题"。

**根因三：只认 EXIF 不认 XMP。** 旧读取走 GDI+ `PropertyItems`，只取 `0x010E` / `0x9C9B`。有些工具（含部分《动态壁纸》早期导出的文件）把标题写在 XMP 的 `dc:title` 里，这类文件在旧代码下同样是"没标题"。

### 13.2 改法：一条链路取词，不再看文件名

新增 `源码\ImageMeta.cs`（约 600 行，本轮唯一的新文件），把"读标题"与"写标题"都收进来。

**读**（`BingWallpaper.GetCaptionForFile(path)`，换图与重绘共用）：

```
① meta：日期键 → 原始文件名键 → 纯文件名键
② EXIF：0x010E ImageDescription（按 UTF-8 严格解码，失败退回系统默认）
        → 0x9C9B XPTitle（UTF-16LE）
③ XMP：APP1 里 dc:title / dc:description 的第一个 rdf:li（顺带做 &amp; 之类的反转义）
④ 都没有 → 返回空串
```

第 ④ 步是关键：**空串就是"不显示"，不报错、不弹提示、不占位**。这符合你定的口径——本地图有标题就正常显示，没有就不显示。

同时删掉了 `SwitchOne` 与 `RepaintCaption` 两处的 `IsBingFile` 前置门（`IsBingFile` 函数本身保留，meta 的键推导还在用它）。顺带修好了一个连带问题：以前本地图点「文字描述…→确定」，重绘函数第一行就被这道门 `return false` 掉，表现为"点了没反应"。

读取也不再走 GDI+ `new Bitmap(path)`（那是把整张 4K 图解码进内存，只为读几个字节的标签）。现在按 JPEG 段结构直接定位 APP1，读 3~4 MB 文件里的几百字节就够，切图更轻。

### 13.3 写：把必应标题按《动态壁纸》的规则写进图片本体

先把你现存文件的写入规则量了一遍（`波尔图大教堂.葡萄牙_UHD.jpg`，GDI+ 逐标签导出）：

| Tag | 名称 | 类型 | 长度 | 内容 |
| --- | --- | --- | --- | --- |
| `0x010E` | ImageDescription | 2 (ASCII) | 30 | `波尔图大教堂, 葡萄牙`（正文，实为 UTF-8 字节） |
| `0x013B` | Artist | 2 | 35 | `Reinhard Schmid/Huber/eStock Photo` |
| `0x8298` | Copyright | 2 | 35 | 同上 |
| `0x9C9B` | XPTitle | 1 (BYTE) | 24 | 同上正文，UTF-16LE + 2 字节 NUL |
| `0x9C9C` | XPComment | 1 | 118 | 必应检索 URL（`https://www.bing.com/search?q=…&form=hpcapt&mkt=zh-cn`） |
| `0x9C9D` | XPAuthor | 1 | 70 | 摄影师 |
| `0x9C9F` | XPSubject | 1 | 20 | `波尔图的青花瓷美景`（必应 `title` 短标题字段） |

长度对得上字节数（`波尔图大教堂, 葡萄牙` = 9 个中文字 + 2 个 ASCII 标点，UTF-8 29 字节 + NUL = 30；UTF-16LE 22 字节 + 2 字节 NUL = 24），说明《动态壁纸》就是这套写法：**正文与摄影师分开存，正文同时写 ASCII 与 XP 两个槽，短标题单独进 XPSubject**。

`ImageMeta.TryWriteTitle()` 就按这套规则构造：

- 把 `必应 copyright`（形如 `亚伯拉罕湖，艾伯塔省，加拿大 (© Guang Cao/Getty Images)`）拆成**正文** + **摄影师**两段；
- EXIF 段整段构造（`FFE1` + 长度 + `Exif\0\0` + 小端 TIFF 头 + IFD0），条目按 tag 升序（EXIF 规范要求），ASCII 槽写 UTF-8+NUL、XP 槽写 UTF-16LE+2 字节 NUL；
- **插在 SOI 之后（有 APP0 就排在 APP0 之后），并剔除文件里原有的 Exif APP1**，所以重复调用结果一致、不会叠加两段；
- 全程只搬字节、**不重解码不重压缩**——4K 壁纸画质一点不掉；
- 落盘用 `File.Replace` **原子替换**（同卷 NTFS 上要么换成新文件、要么原文件不动），不走"先删原图再改名"那条路——那条路一旦改名失败，用户的图就没了；不支持 Replace 的文件系统退化为"原图改名到 `.metaold` → 换入 → 删备份"，换入失败会还原；
- 写完把 `CreationTime` / `LastWriteTime` 还原，避免"写标题"把这张图变成"最新的一张"，打乱你按修改时间排的顺序轮换。

调用点在 `TryDownloadToday`：只有 `useOriginalName = true`（即"存入本地文件夹"这一路）才写，temp 缓存那一路不写（那是临时文件，删了也没意义）。写失败只记一行 Warn，不影响换图，也不影响 meta 兜底。
